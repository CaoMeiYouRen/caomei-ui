## 3. 逐项研判

### 3.1 粒度与数量

- **映射**：本仓的「阶段 / 主线 / 原子条目」正好对应提案的「阶段 / 大条目 / 小条目」。不新建第三套词汇，避免同一事实两套口径。
- **字段承载**：大条目的范围 / 验收 / 非目标 / 依赖 / 交付物 / 风险已由阶段登记记录（`docs/design/governance/<date>-phaseN-registration.md`）承载；小条目的目标 / 验收 / 交付物 / 依赖落在登记记录 §2 表（`条目` / `验收口径` / `文件面`，并新增 `依赖` 列或行内等价写法；**自 2026-11-20 起新登记适用，存量不回改**）。`todo.md` 条目表只保留编号 / 主线 / 条目 / 验收状态指针，不复制两套字段。
- **容量**：现行 §6 为 3–6 条主线；采纳上限 8，第 7–8 条须写「为何不拆阶段」。原子条目建议 10–15、上限 20；超过 15 须在登记记录说明拆分判断，超过 20 必须拆阶段。Phase 34 曾交付 22 条、Phase 38 为 11 条——前者按「存量不回改」保留，后者在建议区间内。
- **不采纳的部分**：不把「大条目 8 要素」作为新的独立正文块复制到 `todo.md`；本仓以登记记录的现有结构承载等价信息，避免 `todo.md` 与登记记录双写。

### 3.2 进度表

- **形态**：6 列 `大条目 / 小条目 / 状态 / 提交 / 审计 / 容量`，行 = 主线；`小条目` 写「已闭环 / 总数」，`状态` 只取 `未开始` / `进行中` / `已闭环` / `已阻塞`，`容量` 写该主线的「计划 → 实际提交数」（默认单位 commits）。
- **位置**：放在 `## Phase N 原子条目` 之前（当前状态段之后），不与条目表混排。原因：`check-stage-counts` 以 `## Phase N 原子条目` 段内的表格行数作为原子条目数；进度表若混入同段，会被误读为条目行。位置规则写入规划规范，后续再让守卫识别表头。
- **当前无表**：Phase 38 已归档，`todo.md` 无当前阶段，因此本次只落规则，不造空表；下一个阶段登记时同步生成。
- **提交列**：登记时为 `—`，执行期填实际 commit；归档时该列与条目表的交付记录、归档块的提交清单三处可互相定位。

### 3.3 提交与审计粒度

- 现状已是「原子条目默认独立提交、独立 Review Gate」；本次只把该实践写成规则，不改变执行方式。
- 合并批次仅限同文件 / 同契约 / 必须同一 commit 才可编译三类，并在登记记录写明合并理由；这与既有「10 语同批」「M6-1 / M6-2 同记录」等先例一致。

### 3.4 归档块字段

- 现有 5 项：阶段名称与时间 / 交付内容与提交记录 / 质量门结果 / 审计结论 / 遗留问题与后续候选。
- 新 6 项：阶段名称与时间 / 交付内容与提交记录（含主线与原子条目状态）/ 质量门结果 / Review Gate 结论与轮次（Pass / Reject、轮次、问题计数与修复情况）/ 未覆盖边界 / 遗留问题与后续候选。
- 现有第 4 项已覆盖 Pass / Reject；新增项主要补「轮次 + 问题计数」与「未覆盖边界」。只对新归档块生效，既有 Phase 33 ~ 38 等块不回改（§3.8）。
- 提案上游 §3.3 的 6 项与 issue 正文的「现有 5 + RG」并不完全一致；本记录以 issue 的项目适配版为准，并把字段定义固定在上面的 6 项，避免两套口径。

### 3.5 归档索引、命名与 roadmap 分片

- **索引 4 列**：保留现有 `阶段 / 时间 / 交付摘要 / 深度归档`，它已经是 4 列；不改成上游模板的 `阶段 / 主题 / 归档文件 / 归档日期`，因为后者会丢失交付摘要、要求重写 34 行，并与 roadmap 阶段表重复。
- **覆盖 / 无重复 / 无正文**：采纳。索引必须覆盖 `docs/plan/archive/` 的全部分片，不得重复登记同一分片，索引行不承载正文块。
- **顺序**：维持**正序**（Phase 0 → 32）。本仓文档结构是「深度归档索引（旧）+ 近线主窗口（新，Phase 33 起）」；只把索引改成倒序会切断时间顺序，并与主窗口的升序阅读顺序冲突。上游模板的「倒序」是默认值，本仓按项目自定顺序处理，理由记录于此。
- **分片命名**：新分片按 `todo-archive-phases-<起>[-<止>].md`；存量 18 个 `phase-*.md` 列为遗留命名，改名批次完成前列入豁免清单，新守卫不得把它们判失败。
- **roadmap 分片**：不采纳 `roadmap-phases-*.md`。本仓 `roadmap.md` 只有 §2 阶段表（每阶段一行摘要）、§4 验收通则与 §5 索引，没有需要外置的逐阶段正文块；再建 roadmap 分片会与 `todo-archive.md` / `archive/index.md` 形成三处重复，违反「同一事实只在一处定义」。若未来 roadmap 出现逐阶段长正文，再按 v1 拆分。

### 3.6 18 个存量分片改名（issue 问题 1）

- **结论：延后为独立批次**，不在本次规则批次做。
- **影响面**：见 §2。实际出现次数是提案估计的数倍，且分布包含 18 个治理记录与归档块回扫句；治理记录多为点时记录，改名会改动其链接路径，按[规划规范 §9](../../standards/planning.md) 只允许「因路径变化产生的链接修正」，不得顺带改正文。
- **批次形态**：建议**单个提交**完成 `git mv` + 链接重指，`git diff -M` 查看重命名；不建议 issue 设想的「先改名、再改链接」两个提交——中间提交会处于链接门禁必失败的状态，违反「每个提交可验证」。若确需分步，第一步只能是不可提交的本地暂存，不进入历史。
- **验收**：链接门禁 exit 0；`git diff -M --stat` 只出现重命名与链接行；剥离链接目标后非空行多重集相等；索引表与主窗口口径句同批重指。
- **触发**：下一次归档压缩批次，或用户单独授权。Backlog 已登记。

### 3.7 主窗口 400 行阈值（issue 问题 3）

- **结论：维持 400 行 warn / 600 行 error。**
- 基线检查器读数 374（本轮规则段 +3 行后 377）；近 14 次压缩多数在越过 400 后触发，2026-11-16（397 行）与 2026-11-20（7 块）按「目标窗口 5 个」触发，说明 400 与「目标窗口」解耦的现行口径仍在工作。
- 下调会立即触发一次无必要的迁出；上调会削弱主窗口可读性。400 与上游模板默认一致，本仓无需改 `check-line-count.mjs`。
- 下一次阶段归档很可能再次越过 400（当前 377 + 新块），届时按既有机械迁出流程处理，不因接近阈值提前改阈值。

### 3.8 归档块 5 项 → 6 项是否追溯（issue 问题 4）

- **结论：只对新归档块生效，不追溯既有块。**
- 既有 33 个阶段块是点时记录；重写会破坏「正文不改写」与 `check:archive-rg-counts` 的计数对账基线。前向统一也是提案自身的第 1 条原则。
- 新块从下一个归档阶段起按 §3.4 的 6 项写；既有块保持原样，索引摘要也不补新字段。

### 3.9 机检（issue「建议」项）

- **索引一致性 + 分片命名**：延后到改名批次。若现在接入命名检查，18 个存量文件会立即失败；若只做索引检查，收益有限且与改名批次重复。改名批次同批接入一个守卫：覆盖 / 无重复仅约束**索引表行**（不约束迁出时点段对同一分片的二次引用）、无正文、命名式 + 存量豁免清单。
- **进度表**：下一次阶段登记时落地。优先扩展现有 `check-stage-counts`（识别进度表表头、行数 = 主线数、状态枚举、归档时 `小条目` 列已闭环数之和 = 条目表 `已交付` 行数），避免新增一个只跑空表的守卫。
- 本次不新增空转守卫：没有当前阶段、没有新分片时，机检只能证明「没有对象」，不能证明规则生效。

## 6. 风险与回滚

- **混合命名期**：新分片用 v1 命名、存量保留旧名，目录会暂时混用。缓解：豁免清单 + 改名批次；新守卫只对新增分片强制命名式。
- **进度表与 `check-stage-counts` 的解析耦合**：进度表放在条目段之外，避免被当作原子条目行；下次登记时用真实阶段验证守卫，而不是只写文档。
- **6 项归档块增大主窗口**：`docs:check:line-count` 可能更早越过 400；按既有机械迁出处理，不提前改阈值。
- **回滚**：本次为文档规则改动，`git revert` 对应提交即可；改名批次回滚为反向 `git mv` + 链接反向重指，以改名前的 commit 为基线复核链接门禁；已按 v1 产出并归档的阶段不回改。
