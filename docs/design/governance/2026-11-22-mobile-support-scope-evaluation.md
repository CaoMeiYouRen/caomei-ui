## 2. 候选盘点与判定

### 2.1 判定口径

- **证据优先级**：`caomei-todo` 需求与架构 > 现有组件的组合能力 > 生态对照。`caomei-todo` 无代码，因此移动候选均为 **产品驱动**，不得表述为「下游已达标」。
- **三条标准**（沿用 `caomei-todo` 架构 §11.5）：桌面形态在触屏上明显不可用、无现成替代、至少 2 个高频页面复用；**全部满足**才按组件立项，否则先做配方 / 文档。
- **容量**：按[规划规范 §6](../../standards/planning.md) 主线 3–6（上限 8）、原子条目建议 10–15（上限 20）；本轮组合若超 15 须说明拆分判断。
- **判定对齐**：逐条判定须与被引标准逐字对齐；不满足者只能列为**例外候选**并交用户裁定，不得在记录中自证「满足」。
- **不新增阶段编号**：本轮不获得 `Phase N`；编号在授权时取「已有最大编号 + 1」。

### M4 移动端能力补齐

- **范围**：① `NavBar`（例外项，D1' ③ 时不适用）——路由级页头，提供返回按钮、标题、尾部操作、可选吸顶与安全区；不接 vue-router，返回行为由 `back` 事件交给使用方。② `SearchBar`——搜索输入 + 清除 + 取消 + 提交，支持受控 `v-model`、`loading`、禁用与空态；复用 `Input` / `Button`，不引入新 primitive；**组件或配方由 D1' 决定**。③ 移动端就绪矩阵——**71 个公开组件页**的移动形态、降级策略与已知边界，数据取 `responsive.md` 与实测，不手写估计。④ 8 个高流量组件页补移动 / 窄屏说明。⑤ 移动壳层示例——页头（NavBar 组件或 Toolbar + 吸顶配方）+ SearchBar + Tabbar + 底部操作条 + 吸顶头部，至少 3 个示例，中英同步。⑥ 真机清单——iOS `dvh` / 触摸滚动 / OTP 自动填充，人工执行并留痕。

## 4. 推荐组合与决策点

**推荐**：**A 移动优先**（M1 ~ M4，4 主线 / 14 条；P2 延后，不发布）。理由：

- 用户已明确移动端方向；NavBar 的页面复用证据来自 `caomei-todo` 的**本仓推断**，且第 1 条不成立、第 2 条存疑（三条未全部满足）——本轮把它作为**用户方向下的例外候选**，由 D1' 明确，不表述为「已达标」。SearchBar 以 P0 搜索页为锚点，先出配方。两者都强于无下游用量的 P2 组件。
- 移动文档缺口可量化（41 个组件页 + 4 个非组件页未提移动；高流量 8 页全缺；仅 2 个移动示例），适合做成可验收的文档批次。
- 通用 Picker 是真实形态缺口，但 `caomei-todo` 明确「iOS 体验差再评估」，当前无真机证据；只评估不实现，避免一次投入滚轮 / 惯性 / 无障碍契约。
- 手势件维持非目标：移动支持不等于引入手势库；推翻须单独裁定。
