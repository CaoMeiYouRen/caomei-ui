# 可选 peer 加载形态取证：字面量说明符 vs 运行期说明符

> 创建时间：2026-11-27
> 触发：Phase 46 M1-1「三路径取证与加载器改造」的第一半（取证）。用户已就第三十一轮评估裁定 **D2 = 运行期说明符 + 强制安装文档**；该裁定在[-第三十一轮评估](./2026-11-27-next-stage-scope-evaluation-31.md)的 Review Gate 中被标为「待 M1-1 三路径取证后确认」，本条即补齐该取证。
> 性质：**取证记录（只读，不改 `src/**`）**；结论交用户确认后方可进入 M1-1 的改造半段。

## 1. 方法与判据

消费方 fixture 建在系统临时目录（`os.tmpdir()`，不在仓库内），`optlib` 为待测构建产物：

- `optlib` 内只有一处加载入口，按两种形态各自实现：
  - **字面量形态**（当前仓库形态）：`await import('qrcode')`；
  - **运行期说明符形态**（D2 选定的修法）：`const specifier = ['qr','code'].join('')` + `await import(specifier)`。
- 消费方 `main.js` 分两种：**使用**（`import { load } from 'optlib'; load()`）与**未使用**（只取命名空间）；
- peer（`qrcode`）分两种：**已安装**（软链到 fixture 的 `node_modules`）与**未安装**；
- 构建器 = 本仓自带的 Vite 8.3.8（`vite build`），判据两条：① 退出码；② 产物里**动态 import 的最终形态**（决定浏览器能否解析）。

> 关键约束：fixture **不能落在仓库内**。首次尝试把 fixture 放在 `node_modules/.exp/` 下，Node 解析沿目录上溯命中了仓库自己的 `node_modules/qrcode`，四组用例全部「构建成功」，属假阴性；改到 `os.tmpdir()` 复跑后得到下表。

## 2. 取证读数

| 加载形态 | peer | 使用组件 | 构建退出码 | 产物中的动态 import |
|:---|:---|:---|:---:|:---|
| 字面量 | 已安装 | 使用 | 0 | `import('./browser-*.js')`（已打包） |
| 字面量 | **未安装** | 使用 | **1**（`Rollup failed to resolve import "qrcode"`） | `import('qrcode')` |
| 字面量 | 已安装 | 未使用 | 0 | `import('./browser-*.js')`（已打包） |
| 字面量 | **未安装** | 未使用 | **1**（同上） | `import('qrcode')` |
| 运行期说明符 | 已安装 | 使用 | 0 | **`import('qrcode')`（裸说明符，未打包）** |
| 运行期说明符 | 未安装 | 使用 | 0 | `import('qrcode')` |
| 运行期说明符 | 已安装 | 未使用 | 0 | `import('qrcode')` |
| 运行期说明符 | 未安装 | 未使用 | 0 | `import('qrcode')` |

## 3. 结论

1. **字面量形态的缺陷属实**：peer 未安装时，**无论是否使用**对应组件，消费方构建都失败（`Rollup failed to resolve import`）。这与 `optional-peer-imports.test.ts` 的「可选」承诺、以及 `docs/design/architecture.md` 现行的「必须一并安装」口径一致，但正是本条目要消除的负担。
2. **运行期说明符能消除构建期失败**：四条路径全部构建成功，构建不再依赖 peer 是否安装。
3. **运行期说明符同时让「已安装」路径失去打包能力**：产物保留裸说明符 `import('qrcode')`，打包器不再把 peer 收进 chunk。浏览器端的模块解析要求 URL 或 import map，裸说明符**无论 peer 是否安装都无法被解析**。因此在浏览器打包场景下，D2 形态把「构建期失败」换成了「运行期失败」，并未真正让组件可用；Node / SSR（如 Nuxt 服务端）里裸说明符可从 `node_modules` 解析，形态可用。
4. 因此 D2 的「强制安装文档」在此形态下**无法兑现**：安装 peer 不改变产物形态，文档若声称「装上即可用」即与实测不符。

## 4. 候选修法（供裁定）

| 方案 | 做法 | 未安装 + 未使用 | 未安装 + 使用 | 已安装 + 使用（浏览器） | 代价 |
|:---|:---|:---|:---|:---|:---|
| **A 运行期说明符（D2 原案）** | 现有加载器改 `import(specifier)` | 构建通过 | 构建通过，运行期报错（含包名与安装命令） | **仍不可用**（裸说明符无法解析） | 零 API 变更；浏览器端功能退化 |
| **B 子路径入口** | 每个内核组件独立子路径入口，包根不再导出 | 构建通过 | 构建失败（点名包名） | 可用 | 从包根移除 3 个组件 = **破坏性变更**，须等 `1.6.0` |
| **C 内核注入 + 运行期兜底** | 组件新增可选 `kernel`（或全局注册）prop：消费方自行 `import` 内核并传入，缺注入时回退运行期说明符并给出含安装命令的错误 | 构建通过 | 构建通过，运行期报错（含包名与安装命令） | **可用**（内核来自消费方模块图） | 新增公开 API（additive），3 个组件 + 文档 + 示例同步 |

## 5. 待裁定

- M1-1 的改造半段取 **A / B / C** 哪一条（默认建议 **C**：唯一同时满足「未安装不阻断构建」与「已安装可用」的方案，且不破坏包根导出）；
- 若取 A：须同时接受「浏览器打包场景下组件不可用」，并把 `docs/design/architecture.md`、发布指南与三张组件页的安装说明改为「运行期解析、由消费方打包器负责」——与「强制安装即可用」相冲突，需明确该口径；
- 若取 B：属破坏性变更，须按 Git 规范 §2 走人工确认，且本阶段（不发布）无法收口。

## 6. 复现方式

fixture 生成与构建脚本见本节所述的临时目录做法；复跑要点：fixture 必须在系统临时目录（不得放在仓库内），peer 的「未安装」须确认上溯路径不命中仓库 `node_modules`。
