# AI 协作规范

本文档定义 caomei-ui 的 PDTFC+ 工作流、搜索优先原则、交接协议与验证矩阵。`AGENTS.md` 为权威事实源，本文档承载细则。

## 1. PDTFC+ 工作流

| 阶段 | 主责 | 关键动作 | 退出条件 |
|------|------|----------|----------|
| **P (Plan)** | `@product-manager` / `@full-stack-master` | 需求澄清、范围判定、验收标准、`todo.md` 对齐、受影响文件清单 | 需求明确、验收标准可验证 |
| **D (Do)** | `@full-stack-master` / `@frontend-developer` | 按方案实现，遵守开发规范 | 自检 `lint` + `typecheck` + 定向测试通过 |
| **A (Audit)** | `@code-reviewer` | Review Gate，输出 Pass/Reject 与问题分级 | 所有 blocker 关闭且验证矩阵满足 |
| **V (Validate)** | `@ui-validator` | 浏览器渲染、响应式、主题、暗色验证 | 验证通过或显式说明跳过理由 |
| **T (Test)** | `@test-engineer` | 测试补强与回归验证 | 测试通过且覆盖率不回退 |
| **F (Finish)** | `@documentation-specialist` + `conventional-committer` | 文档与规划同步、单次提交 | 文档同步、提交完成（不 push） |

### 1.1 阶段去重

- **P**：`@product-manager` 主责，其他角色只提供上下文。
- **D**：同一事项同一时点只有一个实现主责。
- **A**：`@code-reviewer` 是唯一 Review Gate，开发者自检不等于审计通过。
- **V**：`@ui-validator` 主责，`@test-engineer` 不替代可视审计。
- **T**：`@test-engineer` 主责，`@code-reviewer` 只审测试质量。
- **F**：`@documentation-specialist` 与 `@product-manager` 负责收口，不回写未确认结论。

## 2. 搜索优先原则 (Search-First)

遇到以下情况**必须先搜索**，禁止仅凭训练记忆生成答案：

- 同一问题修复失败 >= 2 次，或根因不明确；
- 涉及不熟悉的库/框架/API、跨平台差异或安全合规判断；
- 需要外部文档、版本迁移指南或社区方案支撑决策。

搜索要求：多语言检索、多源交叉验证、工具降级备选；优先采纳 L1（官方文档）与 L2（权威社区）来源，标注来源版本与时间。

适用场景举例：Reka UI primitive 行为、tsdown 构建配置、Vue 3.6 兼容性、semantic-release 插件配置。

## 3. 交接协议

- 交接必须携带：任务目标、验收标准、受影响文件清单、已完成阶段、已验证证据、未覆盖边界。
- 审计调用按 §3.1 声明 `audit-depth` 与时间盒；并发分区按 §3.2；单模块大改动按 §3.2.1 拆分并可与实现并行；用时核验按 §3.3；**轮次上限与范围冻结按 §3.4**。
- 提交必须晚于 Review Gate Pass：先提交后补审判 blocker；已发生的补救只能用新提交（不改写历史、不推送）。
- 审计证据必须与最终 revision 对齐：源码（含 V 阶段后的 CSS 修复）变更后须重跑 `pnpm build` 与浏览器验证并更新证据，陈旧证据判 blocker。
- UI 类改动可在 D 阶段预先用 `@ui-validator` 采集浏览器证据并随审计提交，以满足 Review Gate 对 UI 证据的要求；正式 V / T / F 阶段仍须在 A Pass 后进入。
- 批次粒度阈值见 [规划规范 §5](./planning.md#5-任务粒度约束)；含 barrel `index.ts` / 类型 / 测试的组件需为该批保留「仅本批导出」的中间版本（或按提交分步添加导出），保证每步可构建。
- `docs/**`（`.vitepress` 与 `examples`）已纳入 `vue-tsc`（`pnpm typecheck:docs`，见 [文档与演示站设计 §9](../design/documentation-site.md)）；示例访问未声明插槽字段等类型问题会在类型检查阶段暴露。

### 3.1 审计调用协议（audit-depth 与时间盒）

审查投入与改动风险匹配，不应对所有改动一视同仁长时间分析。`audit-depth` 决定审计者「怎么核验、花多长时间」，与 §4 验证矩阵正交（后者决定最低证据门槛，缺失即 `Reject`）。本表为 `audit-depth` 的唯一权威定义，`code-reviewer` skill / agent 只链接引用、不重复抄写：

| audit-depth | 适用改动 | 审查范围 | 时间盒 |
|:---|:---|:---|:---:|
| `quick` | 文档措辞、重命名、测试补强 | 只核验验证声明（lint / typecheck / 定向测试结果）+ diff 概要一致性 + 明显错误；禁止跑实验、定向测试或翻全量源码 | ≤ 5 分钟 |
| `standard` | 常规业务逻辑、模块内改动、dev 工具链配置 | 正确性 + 边界 + 测试覆盖；定向抽查 ≤ 3 个关键文件；配置类允许 1 条最小生效性验证命令 | ≤ 10 分钟 |
| `deep` | 发布流程、安全 / 鉴权、外部调用、数据写入、运行时 / 发布配置与依赖版本变更、agent / skill 定义、本审查协议自身的档位 / 时间盒定义变更 | 全量 checklist + 针对性验证（临时仓库 / 本地实验 / 验证命令按需执行） | ≤ 20 分钟 |

调用方（`@full-stack-master` 或用户）发起审计时**必须声明**：

- `audit-depth`（`quick` / `standard` / `deep`）+ 理由；
- **时间盒**：单分区取该档位上限，并发分区按 §3.2 取值；复审只重算时间盒（按修复点落档的时间盒上限，且不超过上轮时间盒），档位仍按「适用改动」判定；
- 变更文件清单、已验证证据摘要（lint / typecheck / 测试结果 + 关键断言行号），复审时附上轮问题编号。

约束：

- 未声明 `audit-depth` 时按 `deep` 防御执行，会显著拖长用时——小改动必须主动声明 `quick`。
- **配置类改动至少 `standard`**（lint / 构建 / CI / glob / ignore 规则、依赖清单等）：其正确性取决于生效性（匹配是否命中、覆盖是否完整），而工具退出码与常规成功路径无法区分静默失效；`quick` 禁止额外验证命令，`standard` 及以上显式允许 1 条最小生效性验证命令（如实际 glob 命中数、`git check-ignore` 结果）。
- **档位取严**：改动同时命中多个「适用改动」条目时，取更高档位。
- **协议本体变更按语义定档**：修改 §3.1–§3.3 中会改变档位判定或时间盒数值的定义（含 §3.2 触发阈值）时按 `deep`；纯措辞 / 排版 / 链接修订仍按 `quick` 行执行；降档须在声明中论证不改变任何判定结果。
- 审计 prompt 携带「已查证事实」，避免审计者从头翻源码。
- 复审只审修复点 diff，不重复全量审查。

### 3.2 并发分区审计（仅大改动）

- 触发条件：涉及 **≥ 2 个独立模块**，且 diff 规模较大（默认文件数 > 8 或新增行数 > 400）时，调用方**必须按模块划分，并行发起多个 `@code-reviewer` 审计任务**，再汇总结果。
- 分区维度只有模块：单模块大改动不适用并发，按 §3.2.1 拆分后再审。
- 各区变更规模之和仍须满足任务粒度约束（默认 10 文件 / 800 行新增，见 [规划规范 §5](./planning.md#5-任务粒度约束)）；超限先拆分批次，不得用分区规避阈值。
- 各分区独立出结论；汇总方（主审或调用方）**合并去重、取最严结论**——任一分区存在 blocker，整体即 blocker。
- 并发分区的总时间盒 = 各分区时间盒的最大值（并行执行，不累加）。
- 小改动不得并发。

### 3.2.1 单模块大改动的拆分与「审查 / 实现」并行

- 单模块（如单个组件目录）规模超阈值时，**先按「交付面」拆成多个原子批次**再逐批提交，典型切分：
  1. **交互核心**（取值模型、组件结构、事件）；
  2. **a11y 与本地化**（可访问名 / `aria-*` / locale 命名空间）；
  3. **主题与响应式**（亮暗、断点、覆盖配方）；
  4. **文档与示例**（中英页面、示例、迁移映射）。
- 每批自带断言与最小验收标准，独立走 PDTFC+ 与 Review Gate；批次顺序提交，不得同文件并发改。
- **审查可与后续批次的实现并行**：审查是只读的（§3.2 各分区、§3.4 各轮均只读），因此「批次 N 的审查」与「批次 N+1 的实现」可以重叠执行——调用方在等待审查结论期间可直接推进下一批实现，结论返回后按 §3.4 处理。
- 拆分后的批次仍须满足任务粒度约束；不得把一个大条目切成若干不满足最小验收标准的碎片。

### 3.3 真实用时实测（事后校准）

- LLM 无真实时间感知，自报用时是估算值，**不得作为时间盒核验依据**。
- 发起审计前用宿主系统时钟记录启动时间戳（POSIX 用 `date -Is`，PowerShell 用 `Get-Date -Format o`），返回后计算 elapsed，将「实际用时 / 是否超时间盒」回填审计结论与证据记录。
- 审计过程中不要求审计方感知或检查时间；实测超时仅作分级校准信号（连续超时说明档位偏松或时间盒偏紧），不回溯要求补动作。

### 3.4 轮次上限与范围冻结（防无限审查循环）

- **单条目审计默认最多 3 轮**：首轮 + 1 次复审（复审只审 §3.1 所述修复点）。
- **第 2 轮仍 `Reject`** 时，审计方**只输出 blocker 清单**；warning / suggest 一律转为 follow-up（登记 Backlog 或条目说明），**不再阻断该轮**。
- **第 3 轮及以后**须调用方显式声明「新增预算 + 理由」，或直接上报用户决策；不得默认续审。用户明确要求收束时，以「已验证通过 + 残留项如实登记」提交，并在台账写明未取得新一轮 Pass。
- **复审范围冻结**：只审上轮 findings 的修复点与其**直接受影响**的断言 / 产物。以下属新范围，一律记 follow-up、不阻断本轮：
  - 同类别「顺带扫全库 / 全组件」的一致性排查；
  - 衍生重构、命名与分层建议；
  - 与本条目无关的历史遗留问题。
- 每轮结论必须回填 §3.3 的实测用时；**超时即结束该轮并输出已有结论**，未覆盖项按「未覆盖边界」显式列出，不得以「继续深挖」为由延长。
- 调用方发起审计时应在 prompt 中写明「本轮为第 N 轮」「本轮范围」与「时间盒」，审计方按此执行；未声明轮次时按第 1 轮处理。

## 4. 验证矩阵

见 [测试规范 - 验证矩阵](./testing.md#5-验证矩阵)。任何阶段不得用「已本地验证」替代 Review Gate 结论。

## 5. 失败自检

- 连续 3 次同一方案失败时，停止重跑，切换推理模式（根因分析 / 搜索优先）后再继续。
- 发现新事项时先判断是否在当前验收范围；除非阻塞当前交付，否则记录到 backlog，不静默扩大范围。

## 6. Session 协作

- `.session/`（git-ignored）承载任务态：`current-task.yaml`（进度与认知状态）、`runtime-state.json`（运行快照）、`wisdom.md`（跨 session 发现）。权威来源以 `current-task.yaml` 的 `cognitive` 为准。
- 开局恢复与收尾更新的完整步骤见 `todo-manager` skill，本条不重复定义；失败切换见 §5。
- wisdom 活跃条目 >= 20 时执行蒸馏，详见 [Session Wisdom 蒸馏机制](../design/governance/session-wisdom-distillation.md)。

## 7. 反模式

- 未声明验收标准就开工。
- 跳过 Review Gate 直接提交。
- 用「测试通过」等同于「没有风险」。
- 在注释/测试名中写入规划编号（`T001`、`P1-1` 等）。
- 擅自扩大范围或重构无关代码。

## 8. 取数与批量改写纪律

- 取证计数不得只记裸 grep 数字，必须附「命令 + 口径 + 范围 + 快照日期」；语义类标签（如「关闭后焦点回归 N 处」）须逐条人工核对，避免把 `defineExpose` 与注释一并计数。
- 派发子代理时 `subagent_type` 必须使用 agent 文件 frontmatter 的完整 `name`（含中文括号）；只写 slug 会报 Unknown agent type。
- 批量文本替换未命中会**静默通过**，导致「报告已采纳但产物未改」。凡批量改写必须用带 `assert old in s` 的脚本执行，并逐条核对产物。
- 批量脚本按「同名首匹配」改类型会静默删错接口：`types.ts` 中选项接口与 Props 接口常有同名字段。改类型必须锚定接口作用域（先定位 `export interface X` 再在切片内替换），并在替换后按 `rg -n` 逐文件核对剩余声明。
- 证据目录被 gitignore 时，「结论 + 关键实测值须落可提交位置」必须点名排除这些目录（如 `test-results/`、`artifacts/`、`docs/.vitepress/dist/`），否则追溯要求实际落空。
- 改动落在 agent / skill **定义正文**（触发面 / 工作流 / 资源布局）时属 §3.1 的 `deep` 档；若按 `standard` 声明会产出与内容质量无关的协议 blocker，降档须显式论证「不改变任何判定结果」。
